# Maintenance and Task API — Step 8

These are SQL Server-backed APIs. All routes require bearer authentication and `workspaceId`. All mutations require the CSRF cookie/header from `api.md`. Supply the current `version` on edits, assignments, transitions, cost changes and task deletion. IDs in examples are illustrative.

## Permissions and assignments

OWNER and MANAGER can create work, edit non-closed records, assign/reassign staff, change maintenance costs and cancel work. STAFF can list, read, view history and advance only records currently assigned to their own user ID. STAFF cannot create work, edit its content, change costs, assign, delete or cancel it. Another staff member's record returns 404, and list counts/pagination include only the caller's assigned records. Reassignment removes the previous assignee's access immediately on subsequent requests. Workspace membership and role are checked on every request; platform ADMIN has no implicit access.

Assignees must be enabled users with enabled STAFF membership in the same enabled workspace. Assignment bodies use app user IDs, not membership row IDs. Operators can obtain existing membership/user IDs from `GET /api/workspaces/{id}/members`. Team invitations and membership creation/editing APIs remain pending; this module assigns existing staff memberships. Integration tests provision isolated memberships as test fixtures only.

```json
{"version":0,"assigneeUserId":42,"note":"Kiểm tra trong hôm nay"}
```

Set assigneeUserId to null to unassign work that has not started. In-progress/waiting work must be reassigned to another active staff member. Closed work cannot be reassigned. There is no assignment to OWNER/MANAGER through these endpoints.

## Maintenance routes

| Method | Path | Behavior |
| --- | --- | --- |
| GET | /api/maintenance | Search/filter/sort/paginate within caller scope |
| POST | /api/maintenance | Create OPEN request; returns 201 |
| GET | /api/maintenance/{id} | Authorized detail |
| PUT | /api/maintenance/{id} | Edit title, description and priority |
| PATCH | /api/maintenance/{id}/assignment | Assign, reassign or unassign |
| PATCH | /api/maintenance/{id}/status | Explicit workflow transition |
| PATCH | /api/maintenance/{id}/costs | Operator cost update with mandatory note |
| GET | /api/maintenance/{id}/history | Paginated append-only event history |

Create:

```json
{
  "requestCode": "MT-202609-001",
  "propertyId": 1,
  "roomId": 10,
  "tenantId": 20,
  "title": "Sửa vòi nước bị rò",
  "description": "Vòi nước trong phòng tắm",
  "priority": "HIGH",
  "estimatedCost": 200000
}
```

Property is required; buildingId, roomId and tenantId are optional. When roomId is supplied without buildingId, the building is derived from the room. Supplied property/building/room relationships must match. A supplied tenant must have a non-DRAFT contract at the selected location, including historical contracts. The request's location, tenant and code cannot be changed after creation. Code is normalized to uppercase and unique within the workspace. Title is required (max 200); description max 4000. Priority values: LOW, MEDIUM, HIGH, URGENT.

reportedAt is generated by the server in UTC. actualCost starts at zero. The create body cannot set status, assignee, completion time or actual cost. PUT accepts only version, title, description and priority; assignment, costs and transitions use their dedicated routes.

Workflow:

```text
OPEN --assignment--> ASSIGNED --> IN_PROGRESS --> COMPLETED
                                      |  ^
                                      v  |
                                     WAITING
```

Unassigning ASSIGNED returns to OPEN. Reassigning IN_PROGRESS or WAITING preserves its status. Operators can CANCEL any non-closed request. Only IN_PROGRESS may complete. WAITING must resume IN_PROGRESS before completion. COMPLETED and CANCELLED cannot reopen or change their content. Waiting and cancellation require a nonblank note. A status request cannot bypass the assignment endpoint to force ASSIGNED.

```json
{"version":1,"status":"IN_PROGRESS","note":"Bắt đầu kiểm tra"}
```

Cost update:

```json
{"version":2,"estimatedCost":200000,"actualCost":185000,"note":"Đã nhận hóa đơn linh kiện"}
```

Both costs must be nonnegative DECIMAL(19,2)-compatible values. Operators may correct costs after completion with a mandatory explanation; completedAt remains unchanged and history retains the prior snapshots. Cancelled request costs are frozen. Completion time is always set by the server and cannot be supplied by the client. Financial dashboards in Step 10 will use completed maintenance actual costs; a general expense ledger is not part of this step.

A maintenance request does not automatically change room occupancy or availability. Repairs can concern an occupied room, building or property; the contract and room lifecycle rules continue to govern whether the room is rentable.

List filters: propertyId, buildingId, roomId, assignedUserId, status, priority; search matches requestCode/title/description. Sort fields: id, requestCode, title, priority, status, estimatedCost, actualCost, reportedAt, completedAt, createdAt, updatedAt. Enum sorts use their stored text order; use a priority filter for urgency queues. Default sort: createdAt,desc.

## Task routes

| Method | Path | Behavior |
| --- | --- | --- |
| GET | /api/tasks | Scoped search/filter/sort/pagination |
| POST | /api/tasks | Create TODO; returns 201 |
| GET | /api/tasks/{id} | Authorized detail |
| PUT | /api/tasks/{id} | Edit non-closed task content and due date |
| DELETE | /api/tasks/{id} | Soft-delete TODO; version query parameter required |
| PATCH | /api/tasks/{id}/assignment | Assign, reassign or unassign |
| PATCH | /api/tasks/{id}/status | Start, complete or cancel |
| GET | /api/tasks/{id}/history | Paginated append-only history |

Create:

```json
{
  "propertyId":1,
  "roomId":10,
  "title":"Kiểm tra thiết bị phòng 101",
  "description":"Kiểm tra đèn và khóa cửa",
  "priority":"MEDIUM",
  "dueDate":"2026-10-01"
}
```

Property is required and room is optional; they are immutable after creation. PUT accepts version, title, description, priority and dueDate. Due dates are calendar dates in the workspace timezone and may be in the past for existing backlogs. New tasks are TODO and unassigned.

Workflow: TODO → IN_PROGRESS → COMPLETED. Starting requires an active STAFF assignee. Operators can cancel TODO or IN_PROGRESS with a note; STAFF can start/complete their assigned work. Direct TODO → COMPLETED and reopening are rejected. The server sets completedAt on completion. Closed tasks cannot be edited or reassigned.

Only TODO tasks can be deleted. Deletion is soft: the record and history remain in SQL Server, while lists, detail, history and mutation endpoints treat the task as absent. Started work must be cancelled instead. Deleted records still retain references to their original property/room and prevent physical deletion of those referenced records.

Responses include an `overdue` flag. It is true only for TODO or IN_PROGRESS with dueDate before the workspace's current date. The due date itself is not overdue. List filtering uses the same database predicate so counts, pagination and details agree at local midnight; no scheduler is required.

List filters: propertyId, roomId, assignedUserId, status, priority and overdue=true/false; search matches title/description. Sort fields: id, title, priority, status, dueDate, completedAt, createdAt, updatedAt. Default: createdAt,desc.

## History, pagination and consistency

Lists use page (zero-based), size (1–100) and sort (`field,asc` or `field,desc`). History accepts page/size and returns latest event ID first. Every event contains actorUserId, action, previousStatus, newStatus, current assignedUserId, note and UTC occurredAt. Maintenance events also snapshot estimatedCost and actualCost. Content edits record an UPDATE event; this is workflow history rather than a full revision archive of titles/descriptions. Work events cannot be modified or deleted through the API.

Each mutation obtains a work-record write lock, checks its version and writes the record, event and audit entry in one transaction. The same lock protects assignment and staff status changes, so a staff update cannot bypass a concurrent reassignment. Stale writes return 409. Composite foreign keys reinforce workspace/location/assignee/history relationships; database checks reinforce costs, valid states and completion timestamps. Parent relationships remain preserved even for closed records.

Expected errors: 400 invalid fields/relationships/assignee role or missing required notes; 401 unauthenticated; 403 insufficient permission/CSRF; 404 inaccessible or missing records; 409 stale versions, duplicate codes and invalid lifecycle changes. Unknown/inaccessible list filter IDs simply yield no matching rows and do not reveal parent record existence.

## Running and tests

Follow `backend/README.md` for startup. Flyway applies V5; no new environment variables are needed. API_DOCS_ENABLED enables local Swagger. With TEST_DB_URL pointing to `holoka_newconcept_it`, run `./mvnw.cmd '-Pwindows-auth,sqlserver-it' verify` in backend.

OperationsIT verifies creation, assignment, waiting/resumption/completion, costs, history, staff isolation/reassignment, disabled assignees/memberships, scoped locations/tenant links, task CRUD/soft deletion, midnight overdue status, concurrency, validation and SQL constraints. Notifications and alerts remain Step 9; React screens remain Step 11.
